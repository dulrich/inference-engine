## Cold vs warm

**Never average these three classes together** — they differ by two orders of magnitude in TTFT and are produced by different work.

- **cold** (`cache_n == 0`, 1 turn): nothing in the kv cache. Full 12,791-token prefill at **733 tok/s**, and the model itself has to be loaded first. TTFT **28.9 s**.
- **warm, small delta** (`cache_n > 0`, `prompt_n < 1000`, 3 turns): the ordinary agentic turn — the conversation prefix is cached and only the new tool result plus the new assistant turn are prefilled (201–330 tokens). TTFT **0.8–1.3 s**.
- **warm, large delta** (`cache_n > 0`, `prompt_n >= 1000`, 1 turn): a single `Read` of a large file injected 27,229 new tokens in one turn. Prefill at 523 tok/s, TTFT **52 s** — the worst TTFT of the whole session, worse than the cold turn, and it is pure prefill, not model load.

The operational consequence: on this rig a big `Read` is more expensive than a cold start. Tool results are what move local-leg TTFT, not context size per se.

## Cold TTFT decomposes into load + prefill

`ttftMs` is measured by the router (client-visible first byte); `prompt_ms` in llama-server's `timings` is prefill only. On the cold turn:

| component | ms | what it is |
| --- | ---: | --- |
| `ttftMs` (router) | 28,860 | what the client waited for its first byte |
| `prompt_ms` (llama) | 17,456 | prefill of 12,791 tokens at 733 tok/s |
| **difference** | **11,404** | **load/queue** — llama-swap evicting `bge-m3` and loading the 27B weights |

So ~11.4 s of the cold 28.9 s is model residency, not compute, and it is recovered entirely by keeping the model resident. On every warm turn the same difference is 27–133 ms, i.e. router and network overhead only. The reader reports `load/queue ms = ttftMs − prompt_ms` on every row that has both.

## Decode is flat; prefill degrades with cache depth

Decode throughput is **essentially constant at ~30–33 tok/s across the whole session**, from a 12.8k-token context to a 40.8k-token context (33.3 → 31.0 → 30.4 → 30.9 → 30.2 tok/s). Context depth does not meaningfully cost decode speed at this rung.

Prefill throughput is the opposite: it falls monotonically as the cached prefix grows — **733 tok/s** against an empty cache, 523 tok/s at 13k cached, 361 → 279 → **233 tok/s** as the cache reaches 40k. A 3.1× spread. Prefill of a fixed-size delta therefore gets steadily more expensive as the session lengthens, which is what turns a 201-token append into a 0.9 s TTFT late in the session instead of the 0.3 s it would cost cold.

Practical shape of a local-leg Claude Code session: pay ~29 s once, then ~1 s per turn plus ~33 ms per output token, plus a 50 s spike for any turn that reads something big.

## No conversion-leg timings loss

The plan anticipated that the local leg's OpenAI-conversion path might strip llama-server's `timings` object before the telemetry tap could read it, which would have left the report with router-side TTFT and nothing else. **It does not: `upstreamTimings` is non-null on every local-leg `/v1/messages` row in this session** (all seven fields — `cache_n`, `prompt_n`, `prompt_ms`, `prompt_per_second`, `predicted_n`, `predicted_ms`, `predicted_per_second`). Patch 0006's tap reads the upstream object before conversion, as designed. **There is no defect to report to the sibling plan.** The reader keeps the check live anyway: any completion row that arrives with `upstreamTimings: null` is listed explicitly in its own section rather than silently dropped from the statistics.

`/v1/messages/count_tokens` carries no `timings` by design; it is listed in the table but excluded from every timing statistic.

## Sessions on the local leg are time windows, not session ids

`sessionId` is **`null` on every local-leg row**: the conversion leg drops `metadata.user_id` before building the upstream body (see the comment in patch 0006), so the sink has nothing to record. A local-leg "session" is therefore selected as a **time window** — `--since`/`--until` plus `--leg`/`--model` — not by id. `--session` remains available and is the right filter on the hosted legs, where the field is populated.

`kind:"progress"` rows (1 Hz heartbeats sharing the terminal record's `reqId`) are skipped; the reader counts them as a sanity check against `wallMs` — 306 heartbeats over a 306 s session is exactly right.

## Regenerating

Against the live sink (read-only; never rotate or delete these files). A row's `ts` is its **completion** time, so `--until` must sit after the last turn finished — the harness's own end timestamp (`17:04:14Z`) is a second too early and would drop the final turn:

```sh
node docs/tool-calling-gateway/scripts/router-session-report.mjs \
  $HOME/.local/state/inference-router/logs/router-2026-09-13.0.jsonl \
  --since 2026-09-13T16:59:01Z --until 2026-09-13T17:05:00Z \
  --leg claude-local --md
```

Against the committed fixture (this is the gate command — its output is the embedded block above, byte for byte):

node docs/tool-calling-gateway/scripts/router-session-report.mjs \

Pass several files to span a rotation (`router-2026-09-13.0.jsonl router-2026-09-13.1.jsonl …`); the reader streams every file line by line and never reads one whole. `--json` emits the same rows and summary as machine-readable JSON. Exit 2 means nothing matched the window. Gate: `node --test docs/tool-calling-gateway/scripts/router-session-report.test.mjs`.
