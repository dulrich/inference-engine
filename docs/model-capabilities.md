# Model capability metadata — the `/v1/models` contract

**Normative.** This doc pins the field names, types, and semantics of the per-model capability block served by the llama router (`:4811`) under `meta.llamaswap` in `GET /v1/models`. The blocks live as llama-swap per-model `metadata:` in `llama/config.yaml` (schemaless to llama-swap; the schema is enforced by this doc + review, not by the router). llama-swap merges the block **flat** into `meta.llamaswap`, beside its own reserved keys — so consumers read e.g. `meta.llamaswap.context_length`, and capability fields must never collide with llama-swap's own keys (`aliases`, `type`, `unlisted`, and whatever the pinned llama-swap release reserves).

Landed by the `capability-surfacing-and-local-agent-endpoints` plan WP-1 (canary-verified on llama-swap v243, 2026-08-24). Consumers: bench dashboard Serving tab, Open WebUI capability sync (WP-3 script), obsidian-crucible (read-only, programmatic).

## Ground rules

- **Every value must be derivable from, and equal to, the served configuration** — the `cmd:` flags and the live-verified records in `llama/config.yaml`'s own comments. A capability block is a projection of serving facts, never an aspiration. If a `cmd:` changes (context, KV type, MTP, vision), its metadata block changes in the same edit.
- **Three classes of value, one rule each — and the required key set in the Fields table below is normative for every served chat entry, gate-enforced by `bun run check:recipes` (the console's Rust `check-recipes` binary), full stop.** *Advisory* values (`sampling.*`, `max_output.answer_tokens`) are the model publisher's own recommendation rather than a serving fact, so each one carries provenance: an entry in the `sources` map naming an approved source and the `YYYY-MM-DD` date it was verified, or the explicit gap record `{url: "none", reason: …}` — "the card is silent" is a recorded research result, never an empty field. *Projections* (`context_length`, `max_output.reasoning_budget`, every `serving.*` key, `input_modalities`/`output_modalities`, `tool_calling`) cite nothing — a citation for a projection would be a category error — and are checked for **equality with the corresponding `cmd:` flag, or with that flag's documented default when the flag is absent**: no `-ctk`/`-ctv` ⇒ `serving.kv_cache_type: "f16"`, no `--reasoning-budget` ⇒ `max_output.reasoning_budget: -1`, `serving.flash_attention` ⇔ `-fa on` in `cmd:`, `"image" ∈ input_modalities` ⇔ `--mmproj` in `cmd:`. *Live-probed*: `reasoning` alone, which no flag determines (`--reasoning off` implies `none`, but `budgeted` vs `request-controllable` is a probe result) — it is checked only for membership of the enumeration below, and its evidence bar stays exactly where it is written, in the levels table. **The recipe audit (the `bench-dashboard-serving-control` plan WP-2) landed the conforming config and turned the gate on: every served chat entry in `llama/config.yaml` carries the full required key set today, and `bun run check:recipes` is a numbered gate in the console's contract — a new or edited chat entry that omits a required key, or cites an unapproved source, fails before review sees it.**
- **`sampling` is the sole advisory-provenance exception to the projection principle above** (the `overnight-test-matrix-redesign` plan WP-1, audit B-1). Every other field in this doc is a projection of the served `cmd:` — `sampling` is not: its values are the model publisher's own card-stated sampling recommendation (HF model card / `generation_config.json`), carried here so `/v1/models` consumers get a correct default without re-deriving it per model. `sampling` values change only when a re-verified card source changes them — never as a side effect of a `cmd:` edit (context bump, KV type, MTP) — and the do-not-invent rule applies without exception: a key absent from a model's `sampling` block means the card is silent on it, never "0" or a server default. `sampling` is per-key optional (unlike `eval-harness/inference_research/harness/sampling_table.py`'s harness-side all-or-nothing triple) — a model may carry a partial recommendation (e.g. `temperature`/`top_p` with no `top_k`) because a partial consumer default is still useful. `eval-harness/inference_research/harness/sampling_table.py` (cross-repo) and `metadata.sampling` are two homes for the same underlying research and carry a same-edit drift rule: for the keys both homes carry (`temperature`, `top_p`, `top_k`), an edit to either home's value updates the other in the same session (a `sampling` change in `llama/config.yaml` is mirrored in the eval-harness table); a key only one home carries (e.g. `min_p`, `presence_penalty`, `repetition_penalty` here; the harness table carries none of those) is not drift.
- **Semantics are server-path facts, not model-quality claims.** Fields describe what this serving path accepts and does, verified by response body where noted. Task-level *quality* (e.g. tool-call reliability under agentic load) is explicitly out of scope — that is the bake-off harness's and the Forge eval successor plan's territory.
- **Ids vs aliases**: `/v1/models` `id` is the config model **key**; the append-only alias contract lives on `meta.llamaswap.aliases`. Consumers that persist per-model state should prefer aliases where they can choose; consumers that key by `id` (Open WebUI) are recorded in the consumer registry header of `llama/config.yaml`.
- **Enum evolution is append-only**: new levels/values may be added; existing ones are never renamed or repurposed. Per-model *values* are facts and change when a re-verified serving change lands.

## Fields

| Field | Type | Semantics |
| --- | --- | --- |
| `context_length` | int | The served context window: exactly the `-c` value in this model's `cmd:` (the live-verified safe ceiling, not the GGUF header's theoretical max). |
| `input_modalities` | list | What the serving path accepts. Vocabulary: `text`, `image` (`image` requires a loaded `--mmproj`, body-verified). |
| `output_modalities` | list | What the serving path returns. Vocabulary: `text` (chat completion), `embedding` (`--embeddings` path), `score` (`--reranking` path). |
| `tool_calling` | bool | The serving path accepts a `tools` array and emits structured tool calls for this model (llama.cpp `--jinja` template handling; on the native Anthropic `/v1/messages` route this surfaces as `tool_use` blocks — body-verified on qwen38-27b 2026-08-24). Server-path acceptance, not measured task reliability. |
| `reasoning` | enum | Reasoning-trace support **level** — see the enumeration below. |
| `serving.quant` | string | Weight quantization, exactly as named in the backing GGUF filename (e.g. `UD-Q4_K_XL`, `UD-IQ3_XXS`, `F16`). |
| `serving.kv_cache_type` | string | KV cache dtype: `f16` (llama.cpp default; no `-ctk`/`-ctv` flags) or the explicit symmetric quantized type (e.g. `q4_0` = `-ctk q4_0 -ctv q4_0`). Asymmetric K/V types are banned on this fleet (non-fused-attention fallback — see `llama/config.yaml`'s qwen38 ladder record). |
| `serving.flash_attention` | bool | `-fa on` present in `cmd:` (fused-path engagement live-verified per the config's own VRAM-arithmetic records). |
| `serving.mtp` | bool | Speculative multi-token prediction active (`--spec-type draft-mtp`, sidecar `-md` or embedded heads). Lossless (target-verified) — consumers may ignore it functionally; it is a throughput fact. |
| `serving.moe_cpu_offload_layers` | int (optional) | `-ncmoe` value when present — routed-expert weights of the first N layers held in CPU RAM. |
| `serving.ubatch` | int (optional) | Per-model `-ub` override when present (prefill micro-batch; qwen36's PCIe-streaming amortization). |
| `serving.reasoning_mode` | string (optional) | The `--reasoning [on\|off\|auto]` value when that flag is present in `cmd:`. Absent means the llama-server default, `auto` (detect from template). |
| `serving.reasoning_budget` | int (optional) | The `--reasoning-budget N` value when that flag is present in `cmd:` — `-1` unrestricted, `0` immediate end, `N>0` a token cap on the thinking segment. Absent means the llama-server default (`-1`, unrestricted). Paired with `reasoning: "budgeted"` whenever `N>0`. |
| `sampling.temperature` | float (optional) | Card-recommended sampling temperature. Chat models only; absent means the card is silent, never "0" or a server default. |
| `sampling.top_p` | float (optional) | Card-recommended nucleus-sampling `top_p`. |
| `sampling.top_k` | int (optional) | Card-recommended `top_k`. |
| `sampling.min_p` | float (optional) | Card-recommended `min_p`. |
| `sampling.presence_penalty` | float (optional) | Card-recommended presence penalty. |
| `sampling.repetition_penalty` | float (optional) | Card-recommended repetition penalty. |
| `max_output.reasoning_budget` | int | Projection, mirroring `serving.reasoning_budget`: the `--reasoning-budget N` value served for this entry, and `-1` (the llama-server default, unrestricted) when the flag is absent. Split from `answer_tokens` below because the server splits it — `--reasoning-budget N` caps the thinking segment and `-n, --n-predict N` caps the completion, two independent controls, so one collapsed "max output" integer would be a lie about the serving path. |
| `max_output.answer_tokens` | int | Advisory in provenance (carries a `sources` entry, like `sampling.*`), **bounded in value**: `min(publisher-recommended answer cap, 32000, context_length)` — the *effective* `max_tokens` a consumer may send this entry, never merely what the card says. 32000 is Claude Code's default request `max_tokens` (`CLAUDE_CODE_MAX_OUTPUT_TOKENS`, [env-vars](https://code.claude.com/docs/en/env-vars)), which the router forwards to llama-server unclamped; a Qwen3.8-27B interactive session errored on max response tokens against it (user decision 2026-09-14). The `sources` entry cites the publisher input to that `min()` (or a gap record when no approved source states one — the value is then the ceiling alone). `check:recipes` rule `answer-cap`: a positive int, ≤ 32000, ≤ `context_length`; `-1` is not a legal value here (a gap lives in `sources`). Never a projection — no served flag pins it. **The router now clamps request `max_tokens` down to this value on the `claude-local` leg** (router patch `0010-max-tokens-clamp-claude-local`, landed 2026-09-14): the number is mirrored into the model catalog's `claude-local` entry for that gateway id (the router's model catalog, `maxOutputTokens`), downward only, and `check:recipes` rule `max-tokens-crosswalk` keeps the two equal. |
| `sources` | map | Provenance for the advisory values only — exactly seven entries, keyed by dotted field path in this table's own spelling: the six `sampling.*` keys and `max_output.answer_tokens`. A **sibling of `sampling`, never nested inside it**: the six sampling values must stay plain scalars, because the Open WebUI sync writes them straight into `params` and obsidian-crucible reads the `meta.llamaswap.*` scalars directly. Each entry is either `{url, verified}` — `url` one of the five approved kinds (the lab's own HF model page, the unsloth HF page for the served GGUF, the vLLM recipe, the SGLang recipe, the unsloth serving guide; mechanically, `https://` on `huggingface.co`, `docs.vllm.ai`, `docs.sglang.ai`, `docs.unsloth.ai` or `unsloth.ai` — the latter because `docs.unsloth.ai` has 301-redirected to `unsloth.ai/docs/…` since 2026-09; either spelling of an unsloth guide URL is accepted, and citing the one that actually resolves is preferred), `verified` a bare `YYYY-MM-DD` date in exactly that spelling (never an ISO timestamp, never free text) — or the gap record `{url: "none", reason}`, where `reason` states why no approved source gives a value. |

Optional `serving.*` keys appear only when the underlying flag is present — absence means "macro default", never "unknown". Optional `sampling.*` keys appear only when the model's HF card states that value — absence means "card silent", never "unknown" or a server default (see the `sampling` advisory-exception ground rule above); provenance lives in the sibling `sources` map, never in a `sampling.source` scalar (retired by the recipe audit), and the whole block is absent on non-chat (embed/rerank) models — as are `max_output` and `sources`, which are chat-only for the same reason, and which `check:recipes` therefore never asks of an `--embeddings`/`--reranking` entry. On a served chat entry "the card is silent" is not expressible as silence: each of the six `sampling.*` keys must either carry a value or carry a `sources` gap record naming it.

### Per-model provenance notes

Recorded only where an approved source **contradicts** a value already landed — a source that merely confirms a landed value needs no note (the `sources` entry is the record).

- **`nemotron-4b` `sampling.top_p` = 0.95, not 1.0** (recipe audit, 2026-09-14). Two approved sources disagree by *task*, not by fact: NVIDIA's own card states `temperature=1.0, top_p=0.95` for **reasoning tasks** (and `0.6/0.95` for tool calling), while the unsloth Nemotron 3 guide states `temperature=1.0, top_p=1.0` for **general chat** (and `0.6/0.95` for tool calling). This entry serves general chat/reasoning traffic on this fleet and the landed value follows the lab's own card, so `sources."sampling.top_p"` cites the card, not the guide. The divergence is a real fork in the upstream advice, not a stale value — a future re-verification that wants `1.0` needs a task-scope decision first, not just a re-read.

## `reasoning` support levels

Enumerated, append-only. The level records **observed behavior on this serving path**, live-probed by response body — never inferred from model cards.

| Level | Meaning | Evidence bar |
| --- | --- | --- |
| `none` | No reasoning channel on this serving path (embedding/rerank paths; a chat model that emits no reasoning trace; or a chat entry that disables reasoning at the server with `--reasoning off`). | Path shape, or a default-request probe showing no `reasoning_content`. A `--reasoning off` entry qualifies on path shape — that is the flag's documented job (`llama-server --help`: "Use reasoning/thinking in the chat ('on', 'off', or 'auto'…)") — and is confirmed by a default-request probe when the entry first goes live. |
| `budgeted` | Emits a reasoning trace, and the trace **length** is capped by the served `--reasoning-budget N` (`N>0`): when the budget is exhausted llama-server closes the thinking segment — injecting `--reasoning-budget-message` before the end-of-thinking tag, when one is configured — and continues into `content`. Request-level suppression still works on top, so this is `request-controllable` *with a ceiling*, not instead of it; the cap itself is **not** request-overridable (a request-level `reasoning_budget` field is silently ignored — it exists only as a server flag). | The served `cmd:` carries `--reasoning-budget N` with `N>0`, **and** that value has passed a baseline-vs-budget needle/recall regression against the same entry unbudgeted. The gate is not ceremonial: `docs/test-matrix-results.md` records `qwen38-27b-iq3s` (q4_0/131072) failing three needle probes at `--reasoning-budget 128` — a recall regression, not a truncation artifact — so a budget is a serving fact only once re-measured. |
| `request-controllable` | Emits a reasoning trace by default (`reasoning_content` on chat completions, `thinking` blocks on `/v1/messages`) **and** a request-level control is live-verified to suppress it: `reasoning_effort: "none"` yields a response with no reasoning trace and intact `content`. | Paired probes (default + `reasoning_effort: "none"`), both body-verified. |
| `always-on` | Emits a reasoning trace and no request-level control is verified to suppress it on this path. | Default probe shows the trace; the suppression probe failed or has not been run. Reserved — no current model carries it. |

Consumer guidance: a `budgeted` model is a `request-controllable` model with a server-side ceiling on trace length — clients read it as "reasoning is on, but it cannot run away"; the ceiling exists because an unbounded trace on an agentic client can exhaust that client's own output-token maximum mid-answer. On a `request-controllable` model, clients that don't want reasoning tokens (or need `content` populated within tight `max_tokens` budgets — the documented reasoning-budget-truncation pattern) should send `reasoning_effort: "none"`. Crucible's vision requests already depend on exactly this for gemma.

## Consumer notes

- **Dashboard** (Serving tab): renders this block per alias, joined with (never replacing) the full parsed-flag table.
- **Open WebUI**: does not discover capabilities from `/v1/models`; `scripts/sync-openwebui-capabilities.py` pushes them via Open WebUI's own admin API, keyed by `/v1/models` `id` (= model key — an id rename orphans that model's Open WebUI row until the next sync; the script **never deletes**: as of 2026-09-14 it deactivates the orphans it provably owns and reports the rest as `UNMANAGED`, see Retirement below). Registry row in `llama/config.yaml`'s header.
  - **Invocation**: `OPENWEBUI_URL=... OPENWEBUI_API_KEY=... python3 scripts/sync-openwebui-capabilities.py [--router-url http://127.0.0.1:4811] [--catalog <path>] [--policy <path>] [--only MODEL_ID ...] [--apply]`. Both `OPENWEBUI_URL` and `OPENWEBUI_API_KEY` (or the equivalent `--openwebui-url`/`--openwebui-key` flags) are required with no default — nothing is read from a config file and the key is never logged. `--catalog` defaults to the router's model catalog (`<repo>/router/catalog/…`) (the visibility and effort-ladder source) and `--policy` to `<repo>/scripts/openwebui-policy.json`, each resolved from the script's own location and never from the cwd; a missing or malformed one of the two stops the run before the first HTTP call. The retired `--visibility`/`--gateway-config` flags are an error (exit 2) naming `--catalog`. Dry-run (no `--apply`) is the default: it prints the intended per-row diff and makes no mutating call; for a model with no existing row it prints `CREATE` (`DERIVE` for a derived effort row) plus the **intended** `is_active`, never a transition off an observed value it does not have. `--apply` performs the sync and is idempotent — a second `--apply` run immediately after the first prints an empty diff, since every pushed value is a pure function of the router's live `/v1/models` response **plus the router's model catalog and `scripts/openwebui-policy.json`** (the declarations are the reason the apply path needs no router restart: a freshly-toggled model's desired visibility is read from the file, not from a listing that would not change until one).
  - **Enumeration**: the script reads the complete row set as `GET /api/v1/models/base` ∪ `GET /api/v1/models/export` (live-verified 2026-09-14) — `/base` returns only rows with `base_model_id: null`, so the derived effort rows are invisible there, while `/export` returns exactly the rows that have one, including inactive ones. A single row is re-read via `GET /api/v1/models/model?id=<id>`, which serves both kinds.
  - **Trigger**: this sync runs on a timer — **once per minutely dispatcher pass, including a pass that carries no request**. the serving dispatcher's `_reconcile` (line 271) is called unconditionally from `:398`, immediately after the declaration is staged, on every pass whose declaration is readable. So a change to the catalog's visibility (`consumers`, `exposures`), to `scripts/openwebui-policy.json`, to a catalog `effortKwargs`, or to this script is reconciled within a minute by waiting — and a projection that is failing keeps retrying from the declaration every pass, which is the self-heal the serving plane promises without a retry queue (it was previously per-request and therefore not self-healing at all; measured in the `2026-09-14-tn-code-review` review F2, fixed by WP-R4 of the `post-audit-architecture-and-reconciliation-remediation` plan). A manual `--apply` remains available and is still the way to reconcile immediately rather than at the next minute boundary.

    | Open WebUI field | Source | Notes |
    | --- | --- | --- |
    | `meta.capabilities.vision` (bool) | `"image" in meta.llamaswap.input_modalities` | Open WebUI's native vision toggle; merged into the existing `capabilities` dict, other keys in it are preserved. |
    | `meta.description` (string) | Composed from `name` + `meta.llamaswap.tool_calling`, `.reasoning`, `.context_length`, and `.serving.*` (quant, KV cache type, flash-attention, MTP, MoE offload, `-ub`) | Full overwrite of this one key; deterministic (no timestamps), so it only changes when the underlying serving facts change. |

  - **Derived effort rows** (the `owui-effort-rows-and-arming` plan, landed 2026-09-14): for every model key whose `claude-local` catalog entry (the one carrying it as `modelKey` in the router's model catalog) has an `effortKwargs` field, the sync owns one extra Open WebUI workspace row per reasoning level — stored id `<model key>--effort-<level>` (append-only under the alias contract; registered in `llama/config.yaml`'s header), display name `<router display name> · <level>` (U+00B7), `base_model_id` = the model key, `params` = the base's sampling keys plus `reasoning_effort: <level>`, `meta` = the same three managed fields as the base plus arming. Levels are the **distinct `reasoning_effort` values** in that `effortKwargs` entry plus `none`, in the canonical order `none, low, medium, high, xhigh` — so the gateway's `high → {reasoning_effort: medium}` and `max → {reasoning_effort: xhigh}` collapse onto `medium`/`xhigh` instead of forking rows, an entry carrying only `enable_thinking` contributes nothing, and an entry with no `effortKwargs` (or a key that is only an `exposures` record) gets no derived rows at all. Today that is `Qwen3.8-27B-UD-IQ3_S` alone: `· none|low|medium|xhigh`. A derived row's `is_active` follows its base's desired value, so hiding a base takes its whole ladder with it. Dry-run labels a derived create `DERIVE`; afterwards it is an ordinary `UPDATE`/`TOGGLE`/`no-op`.
  - **Retirement**: an Open WebUI row matching no current router model key and no currently derivable derived id is a *candidate* only where this sync provably owns it — it carries the `meta.llamaswap` marker the sync writes on every create/update, **or** its id has the `--effort-` derived shape, **or** it is named in the policy's `retire_legacy_ids` (seeded with `gemma-4-12B-it-Q4_K_M`, the one dead row the retired `annotate-models.mjs` created without a marker). An active candidate is retired — `RETIRE <id>`, `is_active: false` via the toggle route, verified by re-read; an already-inactive one is reported as `retired (already inactive)`. Anything else unmatched is printed as `UNMANAGED <id>` and never touched: an admin's or another connection's row is not this sync's to deactivate. **The sync still never deletes.** The candidate set is computed against the unfiltered router listing and the full ladder even under `--only` (so `--only X` cannot make every other model's rows look orphaned), and `--only` never retires anything — it prints the would-be list with a `(skipped: --only)` suffix.
  - **Ownership rule for `params`**: the six sampling keys above are repo-owned and script-synced (the `overnight-test-matrix-redesign` plan WP-5, locked decision — no opt-in flag, part of the normal sync) — they change only when `metadata.sampling` changes in `llama/config.yaml`. `params.reasoning_effort` is repo-owned **on derived `--effort-<level>` rows only** (amended 2026-09-14, the `owui-effort-rows-and-arming` plan audit M3) and stays human-owned, unread and unwritten, on every base row. Every other `params` key (e.g. `max_tokens`, `stream`, any admin-set field) is human-owned; the sync never reads or writes it. `meta.llamaswap.sources` is provenance for the advisory values, never a serving parameter, and is **never** written to `params` — no entry of it, and no part of an entry (`url`, `verified`, `reason`), ever becomes a `params` key; it stays router-metadata-only (see the Fields table above and the script's `SAMPLING_PARAM_KEYS` allowlist, which carries the six sampling keys and nothing else).
  - A model id absent from Open WebUI's admin model list (no admin has opened/customized it yet) is **created** (`POST /api/v1/models/create`, minimal body: id, the router's display name, the three `meta` fields above, and `params` seeded with whatever allowlisted sampling keys the router model carries — `{}` for a model with none); an id with an existing row is **merge-updated** (`POST /api/v1/models/model/update?id=...`, full round-trip of the existing row with only the three `meta` fields and the allowlisted `params` keys changed) — Open WebUI's update route replaces `name`/`meta`/`params` wholesale, so a naive "send only what changed" body would silently drop unrelated fields, which is why the script always reads the current row first.
  - **`is_active` is sync-managed for every router-served id** (user decision 2026-09-14, the `bench-dashboard-serving-control` plan WP-3 — this reverses the earlier rule that it was a separate admin decision the sync never made). Desired value: `"openwebui"` ∈ that model key's `consumers` in the router's model catalog (the `claude-local` entry carrying it as `modelKey`, else its `exposures` record). The route is `/api/v1/models/model/toggle` (wire shape **live-verified 2026-09-14** in the WP-3 hold: `POST …/model/toggle?id=<urlencoded id>` with a bearer and an empty JSON body returns 200 carrying the full model row; `is_active` flipped both directions and read back correctly; a third run with an unchanged declaration made no call), and it is a **toggle, not a setter** — the script compares the desired value against the `is_active` it already read off `/api/v1/models/base` and posts **only** on a difference; a row it had to create is re-read first rather than assumed to have defaulted either way, and the value is read back after the post (probe by body, never status code). Everything else in Open WebUI stays admin-owned. Consequence worth stating: the three embed/rerank keys are walked like any other id and their `[]` declaration makes them explicitly `is_active: false` — intended, and a change from "whatever an admin last set".
- **obsidian-crucible**: may consume, directly from `/v1/models`, exactly the `id` field and the `meta.llamaswap.*` fields enumerated in the Fields table above (`aliases`, `context_length`, `input_modalities`, `output_modalities`, `tool_calling`, `reasoning`, `serving.quant`, `serving.kv_cache_type`, `serving.flash_attention`, `serving.mtp`, the optional `serving.moe_cpu_offload_layers`/`serving.ubatch`/`serving.reasoning_mode`/`serving.reasoning_budget`, and — added 2026-09-14, WP-3 — `max_output` and `sources`) — these are append-only-stable per the ground rules above. Visibility is deliberately **not** on this list and appears nowhere in `/v1/models`: it lives in the model catalog's `consumers`/`exposures` (the router's model catalog), which `/v1/models` on the llama router does not serve. Anything else under `meta.llamaswap` (llama-swap's own reserved keys such as `type`/`unlisted`, or any future experimental key not yet promoted into the Fields table) carries no stability guarantee and may change or disappear without notice.
