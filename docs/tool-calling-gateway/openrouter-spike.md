# OpenRouter tee through the resident router — integration spike record

Live measurement run 2026-08-25 (user-directed: `OPENROUTER_API_KEY` added to gitignored `inference-engine/.env`; test model `z-ai/glm-5.2:free` — free tier, non-prompt-training provider, user-selected). Successor to the strategic assessment recorded in `plans/router-prefill-keepalive-and-protocol-gaps.md`'s Audit record: *OR OpenAI-compat leg ≈ config-only; OR Anthropic-compat leg needs a live spike; count_tokens decided per-leg*. Rig: transient container `or-spike-rig` from the production image (`fleet-tools-inference-engine-router:latest`, the four-patch 782cd51 build), `--network host`, port 4701, temp config = production `gateway.config.json` + two OR providers, static-key auth on `x-gateway-key`, torn down at close. All observations by response body, never status code.

## Verdict

**Both OR legs work through the existing four-patch engine with config-only wiring — no patch 0005, no semantic router change needed.** The OpenAI-compat leg (`type openai_chat_completions`, baseurl `https://openrouter.ai/api/v1`) behaves exactly like `claude-local`. The Anthropic-compat leg is real: OR serves a genuine Anthropic-protocol `/api/v1/messages` (Anthropic-shaped error envelopes, `x-api-key` accepted), and a `type anthropic` provider **with `apikey` set** reaches it — with one measured caveat (client must send *some* bearer; see finding 3). Patches 0003/0004 behave correctly on both OR legs with zero changes.

## Provider wiring measured

```json
{"name":"openrouter","type":"openai_chat_completions","apikey":"<OPENROUTER_API_KEY>","baseurl":"https://openrouter.ai/api/v1","models":["z-ai/glm-5.2:free"]}
{"name":"or-anthropic","type":"anthropic","apikey":"<OPENROUTER_API_KEY>","baseurl":"https://openrouter.ai/api","models":["z-ai/glm-5.2:free"]}
```

**A credential must be configured on any OR provider** (either type): a provider with a configured key gets the client credential replaced via `applyProviderCredentials`; a no-key anthropic-type provider passes the incoming bearer through — which on this fleet would leak the caller's subscription OAuth bearer to OpenRouter. Never wire OR as a passthrough provider.

**`apiKeyEnv` keeps the secret out of the committed config** (verified live): the engine's provider loader resolves `apikey || apiKey || process.env[<apiKeyEnv>]` (also accepts the `apikeyEnv` spelling). A rig configured with `"apiKeyEnv": "OPENROUTER_API_KEY"` and the env var injected at `docker run` authenticated against OR successfully. This is the landing form — the committed `gateway.config.json` never carries the key; compose injects `OPENROUTER_API_KEY` into the container environment.

**Auth-before-pool proof rule** (negative control, measured): OR returns `401 {"error":{"message":"User not found.","code":401}}` for a bogus key *before* any upstream pool check — so every `upstream_429` observed in this spike was an authenticated request. This is what makes the 429-window measurements probative: a gateway-relayed 429 proves the provider's real key reached OR (a leaked dummy client bearer would have 401'd).

## Findings

1. **Model-id parsing survives the embedded slash.** `openrouter/z-ai/glm-5.2:free` resolves to provider `openrouter`, model `z-ai/glm-5.2:free` (first-segment split). A **bare** `z-ai/glm-5.2:free` does *not* reach the OR providers — bare ids resolve down the ordered `[openai, anthropic]` default chain (measured: claude-local model-resolution reject, then hosted-anthropic attempt). The provider prefix is mandatory for OR models.
2. **`/v1/models` discovery interplay**: the rig lists both `openrouter/z-ai/glm-5.2:free` and `or-anthropic/z-ai/glm-5.2:free`. Claude Code's gateway model discovery filters to ids containing `claude`/`anthropic` — so an `openrouter/…` id would **not** surface in the picker, while an `or-anthropic/…` id **does** (substring "anthropic"). Provider naming is a free lever for picker visibility.
3. **Anthropic-compat leg needs an incoming bearer** (measured caveat): with gateway auth supplied only via `x-gateway-key` and no client credential, the anthropic-type leg fails at `passthrough_build` with `ANTHROPIC_API_KEY is missing.` — the passthrough header build wants *a* credential before `applyProviderCredentials` replaces it. Any bearer satisfies it: with `Authorization: Bearer <anything>` (measured with a dummy literal, and with the gateway key itself — the exact Claude Code local-mode `ANTHROPIC_AUTH_TOKEN` posture) the request reaches OR's upstream with the provider's OR key substituted (proof: upstream completion/pool responses, not an OR auth error; the dummy never leaked). Practical consequence: local-mode Claude Code consumers hit this leg with zero friction; bare-curl consumers must send any bearer alongside `x-gateway-key`.
4. **Patch 0003 (error-body passthrough) works on both OR legs, byte-verbatim.** During the measurement window the free pool was upstream-rate-limited (sole provider Decart, `upstream_429`, shared pool, `Retry-After: 5`), which gave a live engineered-error measurement for free: through-gateway 429 body on the OpenAI-compat leg was `cmp`-**identical** to the direct-OR body (OpenAI-shaped envelope, 714 bytes), and the anthropic-compat leg relayed OR's Anthropic-shaped `rate_limit_error` envelope (785 bytes, matching direct). Claude Code sees OR's real error, not the engine's `All target providers failed.` envelope.
5. **count_tokens: OR does not serve it — clean relayed 404.** Patch 0004 derives `https://openrouter.ai/api/v1/messages/count_tokens` on both legs (baseurl-ends-`/v1` rule on the OpenAI-compat leg, `/v1/messages/count_tokens` append on the anthropic leg — same URL either way); OR returns 404 `{"error":{"message":"Not Found","code":404}}`, relayed byte-verbatim (`cmp`-identical to direct). No engine change warranted; consumers should expect count_tokens to fail on OR models.
6. **Free-pool contention is real and structural**: `z-ai/glm-5.2:free` has exactly one endpoint provider (Decart, 256k ctx, 99.9% 30-min uptime) and a shared free pool that 429s under load for minutes at a stretch. The account key is credit-backed (`is_free_tier: false`), so the 1000-free-requests/day tier applies, but throughput on `:free` models is best-effort. Fine for spike/testing; not a reliability tier.
7. **Free-pool degradation forced a model switch mid-spike** (user-directed): after ~40 consecutive 429s and then Decart `upstream_500`s (relayed on both legs: OpenAI-shaped envelope on the conversion leg, Anthropic-shaped `provider_unavailable` on the anthropic leg — more patch-0003 evidence), the 200-path probes ran on **`z-ai/glm-5.3`** (paid, $1.40/M in, $4.40/M out, 1M ctx; whole spike ≈ half a cent). The `:free` id stays configured for testing when its pool recovers.
8. **Streamed + non-streamed completions: all four probes green on both legs.**
   - *Conversion leg non-streamed*: valid Anthropic message; OR's `reasoning` output maps to a proper `thinking` content block, text exact, usage mapped. 2.8 s.
   - *Anthropic leg non-streamed*: OR's native Anthropic body relayed with OR's extra usage fields intact (`cost`, `cost_details`, `speed`, `provider`) — per-request cost visibility for free.
   - *Conversion leg streamed*: correct Anthropic SSE sequence (`message_start` → thinking + text blocks → `message_delta` → `message_stop`); note OR delivered the whole short stream in a ~70 ms burst (upstream buffering), fine for clients.
   - *Anthropic leg streamed*: OR's native Anthropic SSE relayed intact; **quirk**: OR appends a trailing OpenAI-style `event: data` / `data: [DONE]` after `message_stop`, relayed verbatim — unknown SSE events are ignored by Anthropic clients, measured harmless.
9. **Keepalive interplay (patch 0002)**: applies to the OR conversion leg by construction (same `anthropic_messages` conversion branch as claude-local); OR prefill measured sub-second on every probe, so no ping ever armed and none was needed. Not exercised at a ≥15 s gap — no cheap way to engineer one against a hosted upstream; the local-leg live verification (8.7 s-gap ping, `resident-router.md`) covers the code path.

## Config landing decision

**Land both legs in the live `router/gateway.config.json`, config-only** (no patch 0005; the audit's replace-vs-integrate exit trigger is not touched):

- `openrouter` (`openai_chat_completions`, baseurl `https://openrouter.ai/api/v1`, `apiKeyEnv: OPENROUTER_API_KEY`) — conversion leg; keepalive-covered; ids invisible to Claude Code picker discovery.
- `or-anthropic` (`anthropic`, baseurl `https://openrouter.ai/api`, `apiKeyEnv: OPENROUTER_API_KEY`) — native passthrough leg; higher fidelity (OR cost fields, native SSE); picker-visible by substring; clients must send some bearer (finding 3) — Claude Code local-mode posture does.
- Models on both: `z-ai/glm-5.2:free`, `z-ai/glm-5.3`. Model ids are stored identifiers once consumers adopt them — the alias append-only contract applies to these provider names and ids from landing onward.
- Compose (`fleet-tools/fleet/compose.fleet.yml`) injects `OPENROUTER_API_KEY: ${OPENROUTER_API_KEY}` into the router environment (key in gitignored `fleet-tools/.env`); env changes need container recreation (`up -d`), not restart, then `router/smoke-router.sh` green plus one live OR-leg probe.
